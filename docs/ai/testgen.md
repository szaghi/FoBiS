# Generating tests

`fobis testgen` writes a test program for the public procedures of a module. FoBiS builds a skeleton from facts,
the LLM completes it with inputs and checks, and the result is **built and run** before you see it: a program is
kept only when it compiles, runs and actually checks something.

```bash
fobis testgen penf_b_size --mode tests-gnu              # generate, build, run; print the accepted program
fobis testgen penf_b_size --mode tests-gnu --apply      # ... and write it to test/test_penf_b_size.f90
fobis testgen penf_b_size --skeleton                    # no model: the compile-checked skeleton only
fobis testgen penf_b_size -p byte_size --max 4          # only this generic, at most 4 procedures
fobis testgen penf_b_size --context                     # print what the model would receive, run no model
```

## Safety

- Everything is built in a **scratch copy** of the project: the working copy (tracked and untracked files,
  ignored ones excluded) and the fetched dependencies. Your source tree, build directory, test directory and
  fetched dependencies are never written; the copy is deleted at the end.
- Your test directory is written only with `--apply` (or `--output PATH`), and never over an existing file.
- A generated test is **code to review** like any other: it checks what the model expects, computed from the
  procedure's code. A check that passes proves the code does what the model read in it, not that it is right.

## How a test is made

1. **The module's public API** (the same analysis as [`ecosystem impact`](/advanced/ecosystem)): public
   procedures, each specific procedure of a public generic (called through the generic name), and the public
   type-bound procedures of the public, non-abstract types (called on an object, `obj%binding(...)`; generic
   bindings through their name).
2. **The skeleton, from facts.** One test subroutine per procedure declares a local variable for each dummy
   argument and calls the procedure with keyword arguments:

   | Dummy argument | Local variable |
   |----------------|----------------|
   | `intent`, `optional`, `value` | dropped |
   | assumed shape `x(:)`, or bounds that are not constants (`x(n)`) | `allocatable :: x(:)` |
   | `character(*)`, `character(len=n)` | `character(len=:), allocatable` |
   | `character(*), allocatable` (or `pointer`) | a fixed length (256): the actual argument of such a dummy cannot have a deferred length |
   | `class(t)` | `type(t)` (`class(t)` kept when allocatable or pointer) |
   | `class(*)`, assumed rank, procedure arguments | not tested, with the reason |

   The module's own `use` statements are repeated, so the kinds and types of the arguments are known. Long
   statements are continued with `&`.
3. **The skeleton is built** with FoBiS (`fobis build --target`, your fobos mode) in the scratch copy. A test
   subroutine whose declarations or call do not compile is dropped, with the compiler's message as the reason,
   and the rest is built again. With `--skeleton` this is the result.
4. **The model completes the skeleton**: it receives the skeleton, the public API, the code of the tested
   procedures (up to 80 lines each) and, when the project has one, an existing test program for its style.
5. **Build, run, inspect.** The program is built and run (`--timeout`, default 60 s). It is **accepted** only when
   - it builds and exits with status 0,
   - it uses the module and calls at least one of its public procedures,
   - it contains at least one check that can fail inside a test subroutine: `error stop`, a non-zero `stop`, or
     an increment of a failure counter (`failures = failures + 1`).
6. **Otherwise the failure goes back to the model**, which sees its previous attempts: the compiler messages on
   the test program's lines, or the exit status and the output of the run, or what is missing (no check). It is
   told to correct an expected value only when the procedure's code shows it was wrong, never to remove a check
   to make the program pass. At most `--retries` more attempts (default 3).

When no program is accepted, the last attempt is printed (not written) with the reason: a check that keeps
failing may be a wrong expectation, or a bug in the code under test.

## The skeleton

A real run on [PENF](https://github.com/szaghi/PENF), restricted to two specific procedures of the generic
`byte_size`:

```text
$ fobis testgen penf_b_size --mode tests-gnu --skeleton -p byte_size --max 2
Module penf_b_size (src/lib/penf_b_size.F90): building the skeleton in a scratch copy...

Test of module penf_b_size:
  test byte_size (byte_size_chr)
  test byte_size (byte_size_i1p)
  skipped byte_size (byte_size_i2p): over the limit of 2 (--max, --procedure)
  ...

Skeleton (builds; give the inputs values and add the checks):

! Test of module penf_b_size: generated by fobis testgen; review it before committing.
program test_penf_b_size
  use penf_b_size
  use penf_global_parameters_variables
  implicit none
  integer :: failures = 0

  call test_byte_size_chr()
  call test_byte_size_i1p()
  ...
  if (failures > 0) then
    print '(a,i0,a)', 'FAILED: ', failures, ' check(s)'
    error stop 1
  end if
  print '(a)', 'test_penf_b_size: all checks passed'
contains

  subroutine test_byte_size_chr()
    character(len=:), allocatable :: i
    integer(i4p) :: res
    ! TODO: give the inputs values, then check the outputs against expected values
    res = byte_size(i=i)
  end subroutine test_byte_size_chr
  ...
end program test_penf_b_size
```

The skeleton is useful on its own: a scaffold that compiles, with one subroutine per procedure to fill by hand.

How much of a module the skeleton covers, on real libraries (gfortran 16, `--skeleton`, every public procedure):

| Module | Procedures tested | Not tested |
|--------|-------------------|------------|
| PENF `penf_b_size` | 12 | 0 |
| PENF `penf_stringify` | 51 | 0 |
| PENF `penf_allocatable_memory` | 100 | 0 |
| StringiFor `stringifor_string_t` (type-bound) | 126 | 0 |
| FLAP `flap_command_line_interface_t` (type-bound) | 37 | 3: `class(*)` arguments |
| FLAP `flap_utils_m` | 21 | 0 |

## Limits

- **Small models are weak at Fortran.** The loop guarantees that what is kept builds, runs and checks; it does not
  guarantee that the checks are meaningful. Use the largest model you can (see [Local models](/ai/models)) and
  read the result. Measured with `coder-0.5b` on CPU, two procedures of a small module: four attempts in 24 s,
  nothing accepted. The model returned the skeleton with a broken string literal and could not fix it from the
  compiler's message.
- The build must work in the scratch copy: when the project does not build with the mode's compiler (missing
  compiler or MPI wrapper, a dependency not fetched), `testgen` says so and stops.
- Procedures defined in submodules, operators and assignments, `class(*)` and assumed-rank arguments, and
  procedure arguments are not tested.
- `--max` (default 8 with the model) keeps the model's input small: test a large module a few procedures at a
  time with `--procedure`.
- The program is written in the mode's sources in the scratch copy (a target outside the sources is not built).
  With `--apply` it goes to the test directory (fobos `[test] test_dir`, default `test/`); for `fobis test` to build
  it there, the test directory must be among the mode's sources.
